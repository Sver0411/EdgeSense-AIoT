# Design Decisions

> **本文件是工程判断的记录地**，不是架构说明（架构见 `PHASE_0_2_FINAL_DESIGN_FREEZE.md` §12）。
> 每条决策记录：**决策 / 理由 / 被放弃的替代方案 / 触发重估的条件**。
> 冻结后新增条目必须以"修正案"形式追加，并引用触发它的 EXP id 与数据。

---

## D-01 · 为什么 B 与 C 必须同场景冗余部署（相隔 30–50 cm）

**决策**：两个传感器节点部署在**同一房间、相隔 30–50 cm**，测量同一组物理量，互为冗余见证。

**理由**
- Primary RQ 研究的是"单节点传感器故障 vs 空间共享环境事件"。这个区分**只在两个节点互为冗余见证时才有定义**。
- 若 B 放房间 1、C 放房间 2，B 与 C 的差异**主要来自环境差异**，于是无法区分"B 的传感器坏了"和"房间 1 本来就比房间 2 湿"。跨节点证据在这种情况下**完全失效**，而且会得出"跨节点无用"的**错误**结论。

**被放弃的替代方案**
- 不同场景部署（更有"真实部署"的观感）——它测的是**空间变化**，不是**故障判别**。若要展示跨场景能力，应作为**独立演示实验**，不进入 Primary RQ 的评估集。

**触发重估的条件**
- 无。这是 Primary RQ 成立的前提。若部署条件改变，必须重新定义 RQ，而不是沿用结论。

## D-02 · 为什么 vendor 固定版本，而不是复制进 monorepo

**决策**：上游仓库保持独立；EdgeSense 以**固定 commit**用 `git subtree` 引入（**不用 submodule**），配 `scripts/vendor_manifest.py --verify` 防止静默漂移。

**理由**（四维度对照）

| 维度 | 复制进 monorepo | 改为 library | **vendor 固定版本（选）** |
|---|---|---|---|
| Git history | **丢失**（最严重） | 保留 | 保留 |
| 研究清晰性 | **最差**：无法区分"这是 SensorTrust 的既有结论"还是"EdgeSense 的新结论" | 好 | **最好**：vendor 的 commit 就是 baseline 出处 |
| 依赖复杂度 | 最简 | 中 | 中（需 vendor + 校验） |
| 作品集呈现 | 一个巨大的仓库，看不出分工 | 清楚 | **最清楚**：方法类仓库 + 一个系统级仓库 |

**被放弃的替代方案**
- **submodule**：clone 时忘记 `--init` 会**静默缺失文件**。对一个需要长期复现、且要交给评审者的实验项目，静默缺失是不可接受的隐患。subtree 把代码物理复制进来，配合哈希校验即可发现"有人偷偷改了 vendor 的代码"。

**触发重估的条件**
- 上游仓库被删除或私有化，导致固定 commit 不可获取。

## D-03 · 为什么跨节点融合在 Gateway，而不在 Sensor Node

**决策**：`cross-node fusion` 与**最终判定**固定在 **Gateway A**；节点只做节点侧闭环（感知 → 逐通道 validity → SensorTrust → 跨通道 → 本地变化检测 → 自适应采样 → LoRa 传输）。

**理由**
1. **拓扑**：B/C 是星型拓扑的**发送端**，没有任何接收邻节点数据的路径。把跨节点融合放在节点上是**架构矛盾**（Phase 0 §12.2 曾如此画，已在 Phase 0.1 修正）。
2. **空口预算**：节点侧融合需要新增 `Gateway → Node` 的邻节点广播，占用稀缺的空口预算。
3. **故障耦合**：节点采样若依赖邻节点数据，**一个节点掉线会改变另一个节点的采样行为**——把"数据可信度"问题扩散成"系统可用性"问题。
4. **可运行性**：节点侧采样闭环只依赖本节点信息，才能保证单节点掉网时仍能自主工作（环境监测节点的基本要求）。
5. **证据粒度**：跨节点一致性本质上是"两个观测的对比"，它天然需要一个能同时看到两者的地方。

**被放弃的替代方案**
- `Gateway → Node` 邻节点广播 + 节点侧融合：被上述 2/3/4 否定。
- 把判定放到后端：见 D-05。

**触发重估的条件（可证伪、有数据依据）**
- **仅当 EXP-008 实测**表明"网关侧判定的端到端检出延迟无法满足需求"时，才重新评估。届时必须在本文件写明触发它的实测数据。

## D-04 · 为什么 Agent 只读（架构上不存在写路径）

**决策**：Copilot 的工具表**全部只读**；后端 API **只提供 GET**；数据库**只被网关 ingest 写入**。不是"暂时不做"，而是**结构上不存在**写入口。

**理由**
- 目标系统是**真实硬件 + 真实环境数据**。让 LLM 拥有重启设备、改固件、改数据库、控制执行器的能力，其失败模式的代价与收益完全不成比例。
- 项目的核心价值主张是**可信的数据与可追溯的证据**。一个能改数据的诊断助手会同时破坏这两者。
- 把"Agent 只读"从**口头约束**变成**架构约束**，是可被检查的：契约测试里任何写操作工具的出现都会导致测试失败。

**被放弃的替代方案**
- "Agent 可以建议，人工确认后执行"——**v1 不做**。它需要一条写通路，而写通路的存在本身就取消了"结构上不存在"这个性质。若日后要做，必须作为独立项目重新论证。

**触发重估的条件**
- 无。这是项目的立场，不是技术权衡。

## D-05 · 为什么把 SQ2 降级为工程评估，而不是研究问题

**决策**：删除 SQ2 作为研究问题 → **Engineering Evaluation E1**（网关侧融合 vs 后端侧融合的资源 / 延迟 / 韧性代价）。

**理由**
- 网关侧判定与后端侧判定**都发生在 LoRa 数据已经到达网关之后**。两者的差异来自 `serial uplink`、`backend processing`、`resource placement`、`backend availability` 四项——**与是否经过 LoRa 无关**。
- 因此它不是"判别能力"问题，而是**资源与韧性放置**问题，把它当研究问题会让 RQ 列表掺入非研究性内容。

**被放弃的替代方案，以及必须禁止的措辞**
- ❌ "Gateway-side decision avoids LoRa latency" / "网关侧判定避开了 LoRa 往返延迟" —— **该论据是错的**（两者都在 LoRa 之后）。

**触发重估的条件**
- 无。E1 的测量仍然必须做，只是它的归属是工程层。

## D-06 · 为什么用固定密集 5 s 参考采样做 Primary RQ

**决策**：EXP-004 / EXP-005 / EXP-006 期间，两节点统一运行**固定 5 s cadence**，**不启用**自适应采样。

**理由**
- Primary RQ 研究**判别能力**。若此时两节点各自跑自适应采样，则**采样密度本身成为混淆变量**：稀疏采样会降低检出率，与"证据是否有效"混在一起，无法归因。
- 配对成功率也会随 cadence 漂移而变化，进一步污染指标。
- 固定密集参考把"判别"与"采样"两个问题**解耦**。

**被放弃的替代方案**
- 直接在自适应采样下做 Primary RQ：因果归因不干净。
- 与 `adaptive-lora-iot/EXPERIMENTS.md` 的既有立场一致：**"5 秒流是密集参考，不是部署间隔"**。

**触发重估的条件**
- 无。自适应/异步条件下的配对能力另行由 EXP-007 单独验证。

## D-07 · 为什么把 Cross-Channel 的 claim 收窄为"额外 contextual evidence"

**决策**：B2 只声称"within-node cross-channel context 是否提供了超出单通道 SensorTrust 的额外判别信息"，**不是**通用 fault/event 判决器。允许结果为：有改善 / **无改善** / 只对某些 family 有改善。

**理由**
- 原假设"单通道变化 = 故障，多通道同时变化 = 环境事件"有两个独立的致命问题：
  - **反向反例**：真实环境事件**可能只影响一个物理量**（光照事件主要影响 BH1750、湿度事件主要影响 humidity）。单通道真实事件是常态。
  - **正向反例**：**I²C 总线级故障会同时影响 SHT30 与 BH1750 两条通道**——于是"多通道同时变化"完全可能由**一个总线级故障**造成。
- 因此原假设可被直接推翻，必须收窄为可证伪的量化问题。

**被放弃的替代方案**
- 保留原假设并加更多通道判断：会掩盖"多通道同时变化"的歧义性，且无法通过对抗性 fixture。

**触发重估的条件**
- 无。但需注意**预期边界**：BH1750 的光照通道几乎无跨通道耦合，**预期 B2 对光照类事件帮助有限**。若结果确实如此，它是**已知边界的确认**，不是失败。

## D-08 · 为什么把"是否需要时钟漂移拟合"留成有数据依据的判断

**决策**：时间同步 v1 只做 `本地单调时钟 + gateway beacon + session id + gateway 定义的 fusion window + nearest valid sample + freshness 检查`，**不做漂移拟合**。漂移拟合是**升级项**，仅当 EXP-004 实测表明简单同步不足时才引入。

**理由**
- 在**没有 offset / jitter / drift 实测数据**的情况下，把线性时钟漂移拟合写成架构要求，是用未验证的假设支撑复杂度。
- 先把三项量测出来，再决定是否需要更复杂的机制——这样无论结论是"需要"还是"不需要"，都是一个**有数据依据的工程判断**。

**被放弃的替代方案**
- 直接上拟合：可能完全没必要，且增加一个未被验证的失效点。

**触发重估的条件**
- EXP-004 实测 offset/jitter 在目标窗口 W 内超出 tolerance（例如 drift 使 offset 在一小时内漂移到超过 tolerance）→ 引入 `gateway_time ≈ a·local_time + b` 拟合并上报残差。

## D-09 · 为什么 Primary RQ 阶段不做功耗/能耗声明

**决策**：v1 不测电流、不上报焦耳；只报 **UART 时间代理**（`(DATA bytes + ACK bytes) × 10 / 9600` 秒）。

**理由**
- 未测电流时，任何"节能"表述都无法支撑。而这正是 Phase 0 明令禁止的"significant energy saving"类无据表述。
- EventGuard 已确立该限定写法，EdgeSense 沿用。

**触发重估的条件**
- 若日后要做能耗实验，必须**真的测电流**，并作为独立 EXP 呈现。

## D-10 · 为什么 v1 用 PostgreSQL 而不是 SQLite，且不引入时序数据库

**决策**：后端用 FastAPI + **PostgreSQL**（单容器 docker-compose）；**不引入** TimescaleDB / ClickHouse。

**理由**
- EdgeSense 的事件模型里 `evidence_json` / `reason_codes` 是**结构可变字段**，JSONB + 单容器 compose 比 SQLite 的 JSON 处理更顺手，且避免了日后迁移的时间成本。
- 第一版的时序数据量**远未到**需要时序数据库的程度。引入它属于"为了技术名词加依赖"，违反项目硬约束。

**触发重估的条件**
- 数据量或查询复杂度真实到达瓶颈时。

## 变更纪律（冻结后）

1. 不得再做**宏观架构重设计**，除非**真实实验数据**证明某个设计不可行。
2. 任何设计变更必须：① 引用**触发它的 EXP id 与具体数据**；② 以**修正案**形式追加到本文件与相关文档，**不原地改写历史结论**。
3. 上游 vendor 代码**内部一行不改**。
